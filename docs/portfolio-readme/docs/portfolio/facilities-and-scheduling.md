# 시설 운영과 일정: API로 다시 본 기능 지도

기준은 저장소의 `134edd3`입니다. 백엔드의 실제 소스(`backend/src/main`)에서 Spring HTTP 매핑 144개를 확인했습니다. 빌드 산출물·테스트의 중복 경로는 세지 않았습니다. API가 있다는 사실과 Flutter 화면에서 실제로 업무를 끝낼 수 있다는 사실을 구분했습니다.

## 세미나실 한 곳을 운영하는 데 필요한 것

1. **시설 정보와 사용 권한**: 건물, 호수, 별칭, 수용 인원과 관리 그룹이 한 시설에 연결됩니다. 관리 그룹은 자기 공간을 관리하고, 다른 그룹의 사용 요청을 심사할 수 있게 API가 나뉩니다. 시설 사용 승인은 특정 날짜의 예약 승인이 아니라, 그 그룹이 이후 예약을 신청할 수 있는 관계입니다.
2. **운영시간과 예외**: 요일별 기본 운영시간이 있고, 수업이나 점심시간처럼 매주 반복되는 시간은 브레이크 타임으로, 장비 점검처럼 날짜가 정해진 일정은 전일·부분 임시 휴무로 따로 기록합니다. 날짜별 가용시간 조회는 여기에 기존 예약을 반영합니다.
3. **일정과 예약의 관계**: 그룹 일정은 장소 없음, 주소나 장소명 직접 입력, 시스템에 등록된 장소 선택을 구분합니다. 시설 캘린더의 별도 예약 폼은 그룹 일정을 먼저 만든 뒤 별도 예약 요청을 보냅니다. 예약 가능 시간의 표시와 예약 저장 경로는 같은 것으로 간주하지 않았습니다. 일부 저장 경로는 구형 차단 데이터 검사를 별도로 사용하므로, 임시 휴무가 모든 경로에서 동일하게 강제된다고 표현하지 않습니다.
4. **예약 변경과 취소**: 서버에는 수정과 취소가 있습니다. 검토한 시설 캘린더의 예약 상세는 취소 메뉴가 있고, 기존 예약 수정 화면은 그 경로에서 찾지 못했습니다. 시설을 삭제하거나 사용 허가를 회수하는 일과 사용자 예약 하나를 취소하는 일도 별개입니다.

## 반복 일정을 저장하는 방식

개인 캘린더, 수업 시간표, 그룹 일정, 시설 예약은 서로 다른 데이터와 API를 사용합니다. 그룹 반복 일정은 매일 또는 선택한 요일을 종료일까지 전개합니다. 달력에서 각 회차를 따로 조회할 수 있게 개별 일정으로 저장하되, 같은 `seriesId`로 묶습니다. 그 덕분에 한 회차와 그 시점 이후의 여러 회차를 구분해 수정·삭제하는 모델을 만들 수 있었습니다. 장소를 지정한 반복 일정은 각 회차의 장소도 다뤄야 하므로, 단순히 제목을 복제하는 작업과 다릅니다.

## 시연 외에 확인한 기능

| 영역 | API와 화면에서 찾아낸 범위 | README에 넣는 기준 |
| --- | --- | --- |
| 시설 운영 | 시설 정보, 기본 운영시간, 반복 제한시간, 날짜별 휴무, 날짜별 가용시간 조회 | 시설 정책과 예약을 분리해서 설명 |
| 타 그룹 시설 사용 | 사용 요청, 대기 목록, 승인·거절·회수, 예약 가능한 시설 조회 | API와 신청·심사 위젯 소스는 있음. 현재 화면에서 이어지는 신청→승인은 확인되지 않아 구현 화면과 구분 |
| 예약 | 장소별 예약 생성·조회, 예약 수정·취소, 여러 장소의 달력 조회 | 실제 화면에서 확인된 동작과 API만 있는 변경 경로를 구분 |
| 개인 일정·시간표 | 캘린더 일정과 수업 시간표 각각 수정·삭제 포함 | 그룹 일정과 합쳐 표시되는 것처럼 설명하지 않음 |
| 채널 | 글·댓글의 작성·수정·삭제, 채널별 마지막 읽은 위치 및 다중 읽지 않은 수 조회 | 웹 채널 목록은 읽지 않은 수를 연결함. 모바일 채널 목록은 같은 수치를 표시하는 것으로 소개하지 않음 |
| 모집 | 공개 공고, 질문지·지원, 심사, 마감 처리, 보관 목록, 지원 철회, 통계 | 기존 지원→승인 시연과 구분. 목록·보관·통계도 별도 API |
| 계정·운영 | 학교 이메일 확인, 닉네임 중복 검사, 역할 신청, 지도교수 연결, 그룹장 이전 | 연결된 온보딩과 관리용 API를 구분. 실제 인증메일이나 운영 데이터는 사용하지 않음 |
